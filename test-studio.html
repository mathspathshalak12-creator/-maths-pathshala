Strict Integrity Mode

A compact set of content-protection controls for student attempts.
RECOMMENDED
Strict integrity profile
Use all supported deterrence controls together.
When enabled in the student phase:
  • Dynamic student watermark on test screens (name/ID, test and attempt time).
  • One-question-at-a-time presentation to reduce bulk viewing.
  • Copy, paste, context-menu and print-shortcut deterrence where browser support allows.
  • Auto-save status and a clear reconnect/recovery confirmation.
Platform limitation: A normal web page cannot reliably block OS-level screenshots, identify Google Gemini/Google Lens, or detect use of another phone/physical screen. These actions must not be counted as confirmed cheating unless a reliable signal exists. For stronger screenshot controls, a managed native app or supervised kiosk environment is required.
Student save & recovery experience: the student interface will show “Saved” after confirmed autosave, “Saving…” while pending, and a reconnect banner with the restored attempt position after network recovery. Network loss itself will not add a cheating strike.
Strike sequence: First confirmed violation → warning; second → final warning; third → auto-submit and security event log. Back navigation, tab visibility and fullscreen events will be handled in the student test interface. A normal website cannot reliably detect a phone being turned off, a second physical monitor, or activity on another device.
Important: these are saved configuration defaults in this Phase 1 admin prototype. Actual timer pause/resume, answer autosave, browser event detection and server-verified auto-submit must be implemented and tested in Phases 2–3; this standalone admin screen does not itself run student exams.
